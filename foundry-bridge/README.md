# Varrenmoor Foundry Bridge (module 0.5.2)

```
Claude (HTTPS) --POST /rpc, Bearer API token--> relay --WebSocket--> Foundry module (GM browser tab)
```

Foundry modules run inside a GM's browser, so **a GM client must be open** (a dedicated browser window on the Foundry PC works). The module connects *outward* to the relay; nothing new is opened on the Foundry server itself.

## Ops
Read: `ping`, `world_info`, `list {collection,type?,nameContains?}`, `get {uuid}`, `audit_activities` (flags Activity IDs that are not 16 alphanumeric chars), `scene_stats`, `perf_sample {ms}` (FPS/long-frame sample; run it while moving a token with vision on).
Write (off unless the world setting **Allow writes** is on): `create`, `update`, and from module 0.3.0 the pipeline ops `version`, `find_by_flag`, `upsert_by_flag`, `upsert_many`, `delete_by_flag`, `delete`, `set_scene_background`, `set_scene_grid` (flag `flags.varrenmoor.pipelineId`; delete only ever removes documents carrying that flag). No arbitrary code execution. `bridge.ps1 <op> -ArgsFile payload.json` takes a JSON file for large payloads. Deploying the module on Vega: `DEPLOY_MODULE.md`.

## Quick start (recommended)
Install Node 20+ and `cloudflared`, then run `start.bat` (Windows) or `./start.sh`. It installs deps, generates tokens into a git-ignored `.env`, starts the relay on 127.0.0.1, opens a Cloudflare quick tunnel, self-tests it, and prints exactly what to enter in Foundry and in the Claude environment.

## Current topology: GM and relay on Arcturus (LAN, no tunnel)
Foundry (the server) stays on VEGA. The GM plays in a browser on ARCTURUS at `http://VEGA:30000` (or Vega's LAN IP), and the relay runs on ARCTURUS next to Claude and Illustrator. Players will later reach Foundry through the netsec Cloudflare tunnel (`netsec/PLAN.md`); the GM keeps using the LAN address.
1. On Arcturus: `start.bat --local` (remembered as `TUNNEL=off` in `.env`). No tunnel; the relay listens on all interfaces at port 3030, because a page served from `http://VEGA:30000` may not open `ws://127.0.0.1`. Allow Node.js on **Private** networks if Windows Firewall asks.
2. (Older notes, kept for the manual path; with pairing none of this is needed, see "Setting up any set of PCs".) In the GM browser, Varrenmoor Bridge settings: Connect ON, **Use launcher relay URL OFF** (that file lives on Vega and would point at a Vega relay), Relay URL = the `ws://<arcturus-lan-ip>:3030/module` the launcher prints, Module token = `BRIDGE_MODULE_TOKEN` from Arcturus's `.env`. Then F5.
3. `.\bridge.ps1 list -Args '{"collection":"Scene"}'` on Arcturus: it reads `foundry-bridge\client.json` (written by the launcher, git-ignored) and calls `http://127.0.0.1:3030`.
4. Run only one relay. On Vega remove `Startup\Varrenmoor Bridge.lnk`, stop its `node start.mjs` and `cloudflared`, and delete `Data\modules\varrenmoor-bridge\relay-url.json` and `<dataPath>\bridge\client.json`.
5. No URL changes across reboots in local mode. Only re-enter the module token when you rotate it. If Arcturus's LAN IP changes, update the Relay URL (a DHCP reservation avoids this).
6. Asset writes from Arcturus go to `\\VEGA\varrenmoor-3d` (Vega's `Data\assets\varrenmoor-3d`, seen by Foundry as `assets/varrenmoor-3d/...`).

`BIND_HOST` in `.env` overrides the listen address (default: `127.0.0.1` with a tunnel, `0.0.0.0` with `--local`). Local mode sends tokens in plain text over the home LAN; keep it off untrusted networks.

## Managed relay: `bridgectl.mjs` (visible window by default, attaches to a running relay)
```
node bridgectl.mjs start|stop|restart|status|probe|info|logs [--env F] [--state D] [--node EXE] [--target host[:port]] [--hidden] [--terminal auto|wt|conhost] [--cim] [--json] [--secrets]
```
**Attach, don't restart.** `status`/`start` first look at the port (`GET /health`, must answer `ok:true`). A relay that is already running is reported `managed (window|hidden)` if this launcher started it (the PID file matches the health pid) or `attached (unmanaged)` otherwise (for example an old `start.bat` relay); `start` then returns `attached` and changes nothing. Only `restart`/`stop` touch a running relay (the panel asks first). `--target 10.0.0.20:3030` inspects a relay on another PC (read-only: no start/stop, no tokens, because its `.env` is not here); `probe` checks this PC, this PC's LAN address and any `--also host:port`.

**A visible window that cannot freeze.** The default launch opens a window titled "Varrenmoor Bridge relay (close = stop relay)" so you can watch the log. Why not plain `cmd` / `start.bat` as before: a click in a console window starts QuickEdit text selection, and the console then blocks the program's output (and the relay's work with it) until Esc/Enter, which looked like random bridge glitches. So the window runs `relay-window.ps1`, which clears `ENABLE_QUICK_EDIT_MODE` (0x40) and sets `ENABLE_EXTENDED_FLAGS` (0x80) for that console, sets the title and a 5000-line scrollback, then runs `node daemon.mjs --console`: every log line is printed live (it auto-scrolls, nothing is buffered) and is also appended to `run/relay.log`. **Windows Terminal** (`wt.exe`) is used instead when it is installed (selecting text there never pauses output; it runs the same script); if it fails to start the launcher falls back to the console window. The window closes by itself after a deliberate Stop; if the relay dies it stays open with the message so you can read why. Pairing requests also appear in that window (press A to approve, D to deny). `--hidden` (panel: "Hidden mode") starts `node daemon.mjs` with no window at all, as in 0.3.x.

**Survives Illustrator closing.** Both modes are started through WMI (`Win32_Process.Create`, via PowerShell/CIM), so the relay is a child of the WMI service, not of the caller: not in Illustrator's process tree and not in its Job Object. `survival.test.mjs` proves it: a parent is put in a Job Object with kill-on-close, launches the relay, exits, and the job is closed; the window relay and the hidden relay keep running, while a plain `spawn(detached)` control dies with the job. (So hidden mode now always uses WMI on Windows; `--cim` is accepted for compatibility.) Not covered: Windows logoff or reboot (the relay does not survive it; no startup entry is created), and Windows Terminal itself (not installed on the PC where this was built; its argument list is unit tested, the launch is not).
- Config: the same git-ignored `.env` as `start.bat` (tokens, `PORT`, `TUNNEL=off` = listen on all interfaces, `BIND_HOST`; `BRIDGE_PAIRING=off` disables pairing). Missing tokens are generated; existing values are never changed. It writes `client.json` for `bridge.ps1` like `start.bat` does. No Cloudflare tunnel: use `start.bat` for tunnel mode.
- State, all git-ignored: `run/relay.pid.json` (pid, port, bind, mode, start time), `run/relay.log` (rotated at 2 MB), `run/paired-devices.json` (see Pairing), `run/relay.stop` (marker so Stop closes the window).
- `GET /health` returns `{ok, service, moduleConnected, pid, startedAt, replacedLastMinute, pairing:{enabled,canEnable,autoRequest,pending,devices}}`. `restart`/`stop` of an unmanaged relay find its pid with `netstat` and refuse to kill anything that is not `node.exe`.
- `info` prints the relay URLs, listen mode and the module settings; tokens only with `--secrets` and only for a relay on this PC (used by the panel).
- Illustrator: the Foundry tab has a Connect-or-launch / Restart / Stop / Find relays block and the Pair devices list (see `illustrator/README.md`).
- Tests (throwaway ports 8799+, throwaway tokens in temp configs, never the real relay): `node --test foundry-bridge/bridgectl.test.mjs foundry-bridge/attach.test.mjs foundry-bridge/window.test.mjs foundry-bridge/survival.test.mjs` (the last two open a console window for a few seconds), `node --test foundry-bridge/relay/`, `node --test foundry-bridge/module/`.

## Setting up any set of PCs (nothing here is specific to a host name or IP)
Three roles; they may be one PC or three different ones. Replace `<relay-pc>` / `<foundry-pc>` with whatever your PCs are called or their LAN addresses.
| Role | What runs | What to do |
|---|---|---|
| Relay PC | the relay (`start.bat`, or `bridgectl.mjs start`) | Run `start.bat --local` once (remembered). The relay listens on `0.0.0.0:3030`, pairing is **on** by default, and it writes `client.json` (URL + API token) next to Foundry's data folder or, without one, into `foundry-bridge/`. Allow Node.js on Private networks. |
| Foundry GM PC | a browser tab on Foundry | Install module 0.5.0 (see `DEPLOY_MODULE.md`). Open Foundry as `http://<foundry-pc>:30000` (the plain-http LAN address, **not** an https/Cloudflare address). With no address typed, the module looks for the relay beside Foundry: the page's own host at port 3030 (`http://10.0.0.5:30000` means relay `10.0.0.5:3030`); if the relay is on another PC type its address once in the module setting "Relay address". |
| Panel PC | Illustrator with the Varrenmoor panel (and Claude's tools) | Foundry tab > Bridge relay. The panel reads the relay address and the API token from the `client.json` the tools already use: `foundry-bridge/client.json` on the same PC, else `\\<relay-pc>\...\client.json` (host from the attached address, env `FOUNDRY_BRIDGE_HOST`, or `FOUNDRY_ASSETS_DIR` in `foundry-3d/.env`; env `FOUNDRY_BRIDGE_SHARE` overrides the path, `{host}` is replaced; Advanced > Diagnostics lets you pick a file). Nothing to type or copy. |

Then: open Foundry as a GM. The module finds the relay, files a pairing request and shows a 6-digit code. In the Illustrator panel (Foundry tab > Pairing) the same code appears with **Approve / Deny**; the relay window also takes A / D. Approve only when both codes match. The module stores its credential by itself. No token is ever copied by hand.

**Pairing off / on without a restart.** Panel: Foundry tab > Pairing > Turn on / Turn off (and Auto-request on/off). It calls the relay's admin endpoint `POST /pair/config {"enabled":true|false,"autoRequest":true|false}` (API token, private address, never through a proxy/tunnel) and the setting is remembered in `run/paired-devices.json`. A relay that was started by an older `start.mjs` has no pairing file and no endpoint, so it needs **one** restart: close its window and run `start.bat` again (the `TUNNEL=off` choice is remembered in `.env`; pairing is on by default; `BRIDGE_PAIRING=off` in `.env` starts it off). Scripted equivalent (signed or `Authorization: Bearer <API token>` from a LAN PC): `curl -X POST http://<relay-pc>:3030/pair/config -H "Authorization: Bearer ..." -d "{\"enabled\":true}"`.

## Pairing (module 0.5.0, encrypted handshake)
```
GM browser (module, pure-JS crypto)                          Relay (node:crypto)
  GET  /discover ---------------------------------->   { service, protocol:2, relayId, pairing, autoRequest }
  gen ephemeral X25519 key A, nonce nA
  POST /pair/request { commit = SHA-256(A, nA) } -->   gen ephemeral key B, nonce nB
  <-- { requestId, pollSecret, B, nB }
  POST /pair/reveal { A, nA, info sealed under K } ->  checks commit; K = HKDF(X25519(A,B), nA|nB, A|B)
        code = H(A, B, nA, nB) mod 10^6                  same code; "Approve this device?" (panel + relay window)
  shows the code                                          human compares the two codes, Approve / Deny
  POST /pair/poll ---------------------------------->  approved: { deviceId, sealed = ChaCha20-Poly1305_K({secret}) }  (ONCE)
  stores {host, deviceId, secret}; every later connect:
  WS hello {deviceId, cn} -> challenge {rn} -> auth {HMAC(secret, cn, rn)} -> welcome {HMAC proof from the relay, rotation sealed}
```
- **Primitives.** X25519 key agreement, HKDF-SHA256, ChaCha20-Poly1305 (AEAD), HMAC-SHA256. The relay uses `node:crypto` (`relay/seccrypto.js`). The module uses a small vendored pure-JS build of the audited `@noble/curves 1.9.7`, `@noble/ciphers 1.3.0` and `@noble/hashes 1.8.0` (MIT; `scripts/vendor/noble-bundle.js` + `NOBLE-LICENSE.txt`, no CDN, no network fetch) because a Foundry page served over plain `http://<lan-host>:30000` is not a secure context, so WebCrypto (`crypto.subtle`) does not exist there; randomness is `crypto.getRandomValues`. The module runs a known-answer self-test (values produced with Node's OpenSSL) before pairing and refuses to pair if it fails. `foundry-bridge/module/seccrypto.test.mjs` proves both implementations produce identical keys, codes, MACs and ciphertexts in both directions, and rejects all-zero (low-order) public keys.
- **Anti man-in-the-middle.** Both sides derive the 6-digit code from a hash of both public keys and both nonces (a short authentication string). The device commits to its key and nonce before it sees the relay's, then reveals (ZRTP-style), so an attacker cannot grind keys until two codes agree: it would have to fix its keys on each side before learning the other side's values, and then has a 1-in-a-million chance per attempt (and the relay allows 5 requests per 10 minutes per address). A swapped key gives different codes; you press Deny. The device description (name, user, world) is sealed under the handshake key, so a sniffer does not see it.
- **The credential.** A 32-byte per-device secret, delivered once, sealed under the handshake key; a sniffer never sees it. After that it is only used as an HMAC key (challenge-response); the relay proves it knows the secret too, so a fake relay is detected and the module refuses to talk to it. The relay stores the secret in `run/paired-devices.json` (git-ignored, mode 0600) because it needs it to check the HMAC; treat that file like `.env`. The module keeps it in the client-scoped setting `deviceAuth` (this browser only). A paired device wins over the manual Module token; unpaired, the **manual token path (plain `hello {token}`) still works** as the fallback.
- **Signed admin requests.** The panel proves it knows the API token with `X-VB-Auth: v1 ts=... n=... sig=HMAC-SHA256(apiToken, method|path|ts|nonce|sha256(body))` instead of sending the token (5-minute clock window, each nonce once, so a sniffed request cannot be replayed). The plain `Authorization: Bearer` form is still accepted for scripts.
- **Revoke / rotate / expiry.** Revoke (panel) closes that device's live socket (4005), deletes its record; the module then forgets the credential, warns once and does not retry. Rotate (panel), or the last 14 days before expiry, make the relay send a fresh secret sealed under a key derived from the old secret and the connection nonces; the old secret works 5 more minutes so a missed save cannot lock the device out. Protocol-1 devices (0.4.x) are dropped when the relay loads its file and simply pair again.
- **Where pairing is refused.** Everything pairing-related (`/discover`, `/pair/*`, device login on the WebSocket) answers only private/loopback source addresses and refuses any request that carries a proxy header (`CF-Connecting-IP`, `X-Forwarded-*`, `Forwarded`, `X-Real-IP`, `CF-Ray`), so players coming through the Cloudflare tunnel (and a tunnelled Claude) can neither pair nor approve. The module itself refuses to start pairing on an `https://` page (players' address) and says why. Limits per source address: 5 requests per 10 min, 2 waiting at once (5 in total), a 60 s cool-down after Deny, 90 polls/min, 10 failed device logins/min (then close code 4008).
- **What is protected, and what is not (threat model).**
  - Protected against a passive sniffer on the LAN: the device credential, the handshake metadata, the API token used by the panel (signed, not sent) and later device logins (challenge-response; nothing replayable). A recorded pairing cannot be decrypted later.
  - Protected against an active attacker only as far as the code check holds: a man in the middle gets different codes (1-in-a-million to fake per try) and a human who compares the codes and presses Deny stops it. **An attacker who also defeats the code confirmation (or a user who approves without comparing) wins.** Anyone on the LAN can still file nuisance requests (rate limited) or see that a relay exists (`/discover`, `/health`).
  - **Not protected: the traffic itself.** The relay speaks plain `http://` / `ws://` on the LAN. After pairing, the ops and their results (world data, Foundry documents) travel unencrypted; Claude's `/rpc` calls from a LAN PC still carry the API token in a Bearer header (`bridge.ps1`). An active attacker on the path can read or alter that traffic or hijack a socket after login. To close that gap put TLS in front of the relay (Caddy/nginx/Cloudflare Tunnel) or keep the relay on a trusted network. Do not pair on an untrusted network.
  - Windows file permissions: see "Windows file permissions" below.
  - A compromise of the relay PC, the Foundry PC's browser profile or `run/paired-devices.json` exposes the device secrets: Revoke and re-pair.
- **Finding the relay.** Browsers cannot do mDNS or UDP broadcast, so discovery is a fixed endpoint the module probes over HTTP, in this order: the stored pairing's host, the address typed in "Relay address", the page's own host at the "Relay port" (default 3030; plain-http pages only), a relay URL setting that is not loopback. Pressing **Pair with relay** also scans the /24 around the page's host. `/discover` also tells the module when the relay has pairing switched off, so the module says "switch it on in the Illustrator panel" instead of failing silently.
- **Auto-request.** With the module setting "Ask for pairing automatically" (default on) and the relay's Auto-request on (default on, switch in the panel), a not-yet-paired GM browser files its request as soon as Foundry loads (one attempt per page load; never a network scan). Press **Pair with relay** (module settings) or run `game.modules.get('varrenmoor-bridge').api.pair()` to ask on demand; `api.unpair()` forgets the pairing.
- **Approval.** Illustrator panel (Foundry tab > Pairing, from any PC that can reach the relay and has the API token) or the relay window. Nothing is issued before a human approves; requests expire after 2 minutes. The relay only accepts an approval that carries the confirmation code of THAT request (a wrong code is refused, three wrong codes deny the request): the panel sends the code of the request it is showing, and in the relay window the code is deliberately NOT printed: press A, type the 6 digits you read from the Foundry screen, Enter (D = deny the oldest, L = list). A request that does not come from a Foundry page on this network (no browser Origin, an origin that is not `http://<LAN host>:30000`, or an origin that differs from what the device claims) is shown with a WARNING; the panel asks for a second confirmation for those.
- **Browser access (CORS), Host and tunnel mode (review F5, F6).** The device endpoints answer a browser only when its `Origin` is an allowed Foundry page: `http(s)://<private IP / localhost / single-label name / *.local, *.lan, *.home, *.home.arpa, *.internal>:30000` (env `FOUNDRY_PORT` changes the port), the relay's own Host name, or an exact entry of `BRIDGE_ALLOWED_ORIGINS` (comma separated, in `.env`). The allowed origin is echoed back (never `*`) and the private-network header is sent only on request. Admin endpoints (`/pair/list|approve|deny|revoke|rotate|config`) send no CORS headers and reject any request that carries an `Origin` header (web pages cannot call them; the panel and scripts have no `Origin`). Every pairing/admin request must also have a private source address, no proxy header AND a `Host` header that is a LAN name or IP (a public name such as `x.trycloudflare.com` is refused). **Tunnel mode fails closed:** when the relay is started with a tunnel (`start.bat` without `--local`) or with `PUBLIC_URL` in `.env`, `/discover`, `/pair/*` and device login do not work at all (use `start.bat --local` for pairing); `/health` shows only `ok` to non-LAN callers.
- **Robustness (review F1, F2).** Every WebSocket frame and HTTP request is parsed defensively (non-object JSON, aborted bodies, oversize pre-auth frames are ignored or answered, never thrown); `daemon.mjs` and `start.mjs` log (tokens scrubbed) and keep running on an unexpected error (the daemon exits only if more than 20 occur in a minute). At most 16 unauthenticated sockets, 4 KB per frame before login.
- **Admin replay (F12).** A signed admin call is accepted only if its timestamp is newer than the relay's start and than the newest signed call it ever accepted (`run/paired-devices.admin-ts.json`), so a captured request cannot be replayed after a restart. Right after a restart the panel may see "request predates the relay start" once; it retries by itself.
- **pollSecret over clear http (F11).** The request id and poll secret travel in clear on the plain-http LAN. They are now bound to the source address that made the request (a sniffer on another address cannot poll or cancel it) and the secret credential is delivered sealed and once, so the worst a sniffer on the same address can do is make the device re-pair. Unrevealed handshakes expire after 20 s and have their own cap, so they cannot block real requests.
- Tests: `node --test foundry-bridge/relay/pairing.test.js foundry-bridge/module/pairing.test.mjs foundry-bridge/module/seccrypto.test.mjs` (commit/reveal, equal codes, sealed one-time credential, challenge-response login, rotation + grace window, revoke, deny + cool-down, live enable/disable and approval from a different "origin", signed-admin replay/tamper/clock refusal, non-private and proxy/tunnel refusal, https refusal in the module, fake-relay detection, no secrets on the wire or in logs, cross-implementation known answers) and `node illustrator/panel/test/test_bridge_jobs.js` (panel logic against a throwaway relay).

## Two GM tabs fighting (close code 4002)
The relay keeps one module connection; a second authenticated GM client replaces the first (the first is closed with 4002). Module 0.3.0 reconnected on every close, so two GM tabs evicted each other about once per second and Foundry showed "Varrenmoor Bridge connected" each time. Module 0.3.1 does not reconnect after a 4002 close; it shows a single warning ("another GM tab took over ... close the extra tab, or press F5 to take it back"), and notices are rate limited to one per minute per kind. The relay now logs `WARN replacing an existing module client (4002)` and counts evictions in `/health` (`replacedLastMinute`). Until the module is redeployed (DEPLOY_MODULE.md), an old tab still loops: close the extra GM tab.

## Manual install
1. In Foundry: Add-on Modules > Install Module > Manifest URL: `https://raw.githubusercontent.com/snarshmallow/Varrenmoor-Campaign-Homebrew-Spells-Plutonium-Repository/claude/adoring-shannon-yjixst/foundry-bridge/module/varrenmoor-bridge/module.json` (change `claude/adoring-shannon-yjixst` to `main` after merging; rebuild `module/varrenmoor-bridge.zip` whenever the module changes). Then enable it in the world.
2. On a machine that can run Node 20+: `cd relay && npm install`, then set two different random tokens (24+ chars) and run:
   `BRIDGE_API_TOKEN=... BRIDGE_MODULE_TOKEN=... HOST=0.0.0.0 PORT=3030 node server.js`
3. Put TLS in front of the relay (Caddy/nginx/Cloudflare Tunnel) before exposing it to the internet. Do not expose plain HTTP; tokens travel in headers.
4. In Foundry (GM client): Module Settings > Varrenmoor Bridge: enable, set relay URL (`wss://your-host/module`) and the **module** token.
5. Give Claude the HTTPS URL and the **API** token via the environment's secrets, and add the host to the environment's allowed domains.

## Windows file permissions
`mode 0600` does nothing on NTFS: `.env` (both tokens), `run\paired-devices.json` (device secrets, needed in clear for the HMAC login) and `client.json` (API token) inherit the folder's permissions, which are often readable by every local account. The managed relay (`daemon.mjs`) and `start.mjs` therefore run, best effort and without failing if it does not work, `icacls <file> /inheritance:r /grant:r "<you>:F"` on `.env` and `icacls run /inheritance:r /grant:r "<you>:(OI)(CI)F"` on the `run` folder (set `BRIDGE_HARDEN_ACL=off` in `.env` to skip). By hand (PowerShell, in `foundry-bridge`):
```
icacls .env /inheritance:r /grant:r "$($env:USERDOMAIN)\$($env:USERNAME):F"
icacls run /inheritance:r /grant:r "$($env:USERDOMAIN)\$($env:USERNAME):(OI)(CI)F"
icacls client.json /inheritance:r /grant:r "$($env:USERDOMAIN)\$($env:USERNAME):F"      # only the copy inside the repo
icacls . /T /C /Q        # show the result (nothing for Users / Everyone / Authenticated Users should remain)
```
`client.json` that is published to `<Foundry data>ridge\` and read from another PC over a share is NOT restricted automatically (the other PC's account must read it): give that folder read access to that one account only and write access to nobody else. Whoever can write that file can redirect the next `bridge.ps1` call (and its Bearer token) to their own server. `prevSecret` (a rotated-out device secret) is removed from `paired-devices.json` as soon as its 5-minute grace period is over. `.gitignore` covers `client.json*`, so a renamed copy (for example `client.json.old`) is never staged.

## Security notes
- Two separate tokens (plus per-device pairing tokens, see Pairing and its threat model); compare in constant time; module auth times out after 5 s; one module connection at a time.
- Use a dedicated GM user for the bridge tab if you want it distinguishable in logs.
- Rotate tokens if the tab is ever left open on a shared machine.

## Auto-config for Claude Code on another PC (no secrets to paste)
`start.bat` (and `node publish-client.mjs`, if the relay is already running) writes `<Foundry dataPath>\bridge\client.json` with the live tunnel URL and API token. It sits outside `Data/`, which Foundry serves to players. On the other PC, `foundry-bridge\bridge.ps1 <op> [-Args '<json>']` finds it at `\\<host>\C\FoundryVTT resources\bridge\client.json` by itself (host from env `FOUNDRY_BRIDGE_HOST` or `FOUNDRY_ASSETS_DIR` in `foundry-3d\.env`; no host is built in; env `FOUNDRY_BRIDGE_SHARE` overrides the path). Quick-tunnel URLs change on restart; `start.bat` rewrites the file each time. Overrides: `-Config <file>`, or env `FOUNDRY_BRIDGE_URL` + `FOUNDRY_BRIDGE_TOKEN`. The Claude environment secrets screen is for cloud sessions only; a local CLI session does not read it.
